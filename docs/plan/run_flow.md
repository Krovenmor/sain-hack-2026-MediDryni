# Поток online/final-проверки

1. **Получить вход.** `HTTP transport` проверяет `case == 2` и Bearer token. `RunCase` вызывает `GET /case/2/getData?dataset_code=...` с тем же token. До получения dataset никакие room-сессии не создаются: для них нужны `record_id`.

2. **Подготовить контекст.** Данные индексируются по `user_id` и `record_id`. `ai_service` всегда извлекает hints из `events` и `chat_history` один раз на пользователя в рамках `/run`, независимо от заполненности профиля. Core дожидается результата в рамках обычного timeout и общего deadline, затем разрешает параметры по приоритету «профиль → hints → дефолты». Дефолты заполняют недостающие сведения и при успешном ответе AI; при ошибке/timeout AI используются профиль и те же дефолты. Результат переиспользуется для заездов пользователя.

3. **Обработать каждый заезд.** `SleepPlanner` детерминированно строит сценарий R1–R8 и проверяет время, устройства и диапазоны. Для R1 при заселении до отбоя вечерний свет действует с `max(check_in_at, bedtime − 60 минут)` до отбоя; поздний check-in сокращает этот интервал без переноса отбоя. Если заселение в момент отбоя или позже, интервал R1 не создаётся, применяются настройки текущей фазы сценария. Для **каждого** `stays[].record_id` отдельно:
   - `POST /room/session` с `kind=stay`;
   - `POST /room/{session_id}/scenario` с полным сценарием;
   - сохранить пару `{record_id, session_id}` для ответа.

4. **Обработать просьбы в порядке диалога.** Просьбы каждого пользователя выполняются последовательно в исходном хронологическом порядке набора; разные пользователи могут выполняться параллельно в пределах rate limit. Для **каждого** `requests[].record_id`:
   - создать отдельный сеанс `POST /room/session` с `kind=request` даже для будущего отказа;
   - передать в AI текущие 1–2 `utterances` одним вызовом вместе с предыдущей историей только этого пользователя;
   - AI-адаптер проверяет возвращённые `record_id`, один intent для всей записи и slots; при невалидном ответе модели выполняет один retry, при повторной ошибке выбрасывает `AiAgentError`; core применяет deterministic fallback или безопасный отказ без повторного AI-вызова (см. [контракт AiAgent](../contracts/ai_agent.md));
   - через `ActionPlanner` построить ноль или несколько device patch от `initial_state`, профиля и ленты; проверить весь план по `devices`;
   - для допустимых действий вызвать `POST /room/{session_id}/action` для каждого изменяемого устройства в фиксированное время просьбы; для `medical`, `out_of_scope`, `invalid_value` действия не выполнять;
   - сформировать один безопасный reply на всю просьбу с временем последней входной реплики. `done` ставится после успешного действия либо если требуемое состояние уже достигнуто, иначе — `refused`.

5. **Обновить контекст.** Только после обработки текущей записи добавить её utterances и готовые replies в conversation context этого пользователя. Переносится **диалог**, а не состояние устройств: каждая следующая запись использует собственный `initial_state` и новый session.

6. **Вернуть полный ответ.** Локально проверить `Case2Answers` и вернуть HTTP 200:

```json
{
  "stays": [{"record_id": "stay_1", "session_id": "3fa85f64-5717-4562-b3fc-2c963f66afa6"}],
  "requests": [{
    "record_id": "request_1",
    "session_id": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
    "replies": [{
      "role": "agent",
      "at": "2026-11-20T22:00:00+03:00",
      "text": "Уменьшил яркость света.",
      "response_class": "done"
    }]
  }]
}
```

`/case/2/validate` используется только при dev-проверке, из online/final `/run` не вызывается. Ошибка одной записи не должна отменять обработку остальных; при этом отсутствующая или невалидная запись будет оценена как неверная.

Для dev E2E команда создаёт прогон через `POST /runs` с `HACK_TEAM_TOKEN` и вызывает локальный `/run` с выданным `run_token` в Bearer-заголовке. Приложение передаёт этот же токен в `getData` и Room API. Симулятор определяет прогон по токену, поэтому в теле `POST /room/session` достаточно `record_id` и `kind`. На online/final приложение получает Bearer-токен от стенда и передаёт его тем же способом. `run_id` указывается при прямом создании dev-сеанса с командным токеном. Запрос `validate` отправляется отдельно с `HACK_TEAM_TOKEN`.
