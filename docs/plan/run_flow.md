# Как обрабатывается POST /run

## Загрузка набора

Стенд передает в `POST /run` тело `{"case": 2, "dataset_code": "…"}` и заголовок `Authorization: Bearer <run_token>`. HTTP-обработчик извлекает токен, а `RunCase` проверяет номер кейса. С тем же токеном приложение запрашивает `GET /case/2/getData` и обращается к Room API. Для создания сеанса достаточно `record_id` и `kind`, прогон симулятор узнает по токену.

Адаптер проверяет формат набора, затем приложение сверяет связи между записями, индексирует устройства и группирует ленту, диалоги и просьбы по гостям. Из этих данных собирается контекст каждого гостя. [Обработчик прогона](../../src/concierge_service/service/run_case.py)

## Заезды

1. `AiAgent` извлекает предпочтения из профилей, ленты и истории сообщений. На это отводится до 10 минут в пределах общего дедлайна. Если подсказок нет или их обработка завершилась ошибкой, concierge использует профиль и значения по умолчанию. В контекст просьб попадают только принятые подсказки. Если обработать сам профиль тоже не удалось, concierge пропускает заезды и просьбы этого гостя и продолжает прогон для остальных.
2. `SleepPlanner` вычисляет время отбоя в часовом поясе отеля, применяет поправку R8 и строит шаги от заселения до подъема. При позднем заселении сценарий начинается с текущей фазы. Времена, устройства и значения проверяются перед отправкой.
3. Для каждого заезда concierge создает сеанс через `POST /room/session` с `kind=stay` и один раз загружает расписание в `POST /room/{session_id}/scenario`. После подтверждения он сохраняет пару `record_id` и `session_id`. Просьбы потом выполняются в своих сеансах.

## Просьбы

До четырех гостей обрабатываются параллельно. Внутри каждого диалога просьбы идут по времени.

1. Для записи открывается сеанс с `kind=request`, даже если просьба потом получит отказ. Исходные значения устройств берутся из ее `initial_state`.
2. `AiAgent` получает одну или две реплики этой записи, контекст гостя и предыдущие ответы и возвращает одно намерение с параметрами. Например, для сдвига будильника модель возвращает направление и число минут, а новое время вычисляет concierge.
3. Concierge проверяет план по каталогу устройств. Для каждого изменения он отправляет `POST /room/{session_id}/action` с временем `request.at` и сверяет время и значения в ответе симулятора. При сбое оставшиеся действия не выполняются.
4. Гость получает один ответ. Класс `done` означает, что изменения подтверждены или нужное состояние уже было достигнуто. Невозможная, медицинская, посторонняя или нераспознанная просьба получает `refused`. При частичном выполнении ответ тоже получает `refused` и сообщает, что удалось сделать. В историю гостя записываются реплики и поля, изменение которых подтвердил симулятор, поэтому следующая просьба может сослаться на конкретное значение, даже если ответ гостю был коротким. [Обработчик просьбы](../../src/concierge_service/service/request_handler.py)

## Ответ стенду

`Case2Answers` содержит два массива. В `stays` возвращаются идентификаторы записей и сеансов, а в `requests` те же идентификаторы вместе с массивом `replies`. Каждая реплика содержит роль, время, текст и класс ответа. Если создать сеанс не удалось, запись пропускается. Заезд с ошибкой загрузки сценария в ответ тоже не попадает.

Из 45 минут пять секунд зарезервированы на формирование ответа. Если после получения набора истекает рабочий дедлайн, сервер возвращает HTTP 200 с завершенными записями. Если набор еще загружается, сервер возвращает HTTP 504. На dev ответ отдельно проверяет скрипт оценки через `/case/2/validate`. [HTTP-схемы](../../src/concierge_service/transport/http/schemas.py)
