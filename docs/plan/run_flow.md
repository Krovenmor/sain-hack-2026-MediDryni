# Как обрабатывается POST /run

## Загрузка набора

Стенд передаёт в `POST /run` тело `{"case": 2, "dataset_code": "…"}` и заголовок `Authorization: Bearer <run_token>`. HTTP-обработчик извлекает токен, а `RunCase` проверяет номер кейса. С тем же токеном приложение запрашивает `GET /case/2/getData` и обращается к Room API. При создании сеанса достаточно `record_id` и `kind` — симулятор узнаёт прогон по токену.

Адаптер проверяет формат набора. Затем приложение проверяет связи между записями, индексирует устройства, группирует ленту, диалоги и просьбы по гостям. По этим данным у каждого гостя формируется свой контекст. [Обработчик прогона](../../src/concierge_service/service/run_case.py)

## Заезды

1. `AiAgent` извлекает предпочтения из профилей, ленты и истории сообщений. На эту работу выделяется до 10 минут в пределах общего дедлайна. Если для гостя подсказок нет, concierge использует его профиль и значения по умолчанию.
2. `SleepPlanner` вычисляет время отбоя в часовом поясе отеля, применяет поправку R8 и строит шаги от заселения до подъёма. При позднем заселении сценарий начинается с актуальной фазы. Времена, устройства и значения проверяются перед отправкой.
3. Для каждого заезда concierge создаёт сеанс через `POST /room/session` с `kind=stay` и один раз загружает расписание в `POST /room/{session_id}/scenario`. После подтверждения сохраняет пару `record_id` и `session_id`. Дальнейшие просьбы выполняются в собственных сеансах.

## Просьбы

До четырёх гостей обрабатываются параллельно. Внутри каждого диалога просьбы идут по времени.

1. Для записи открывается сеанс с `kind=request`, в том числе если просьба впоследствии получит отказ. Исходные значения устройств берутся из её `initial_state`.
2. `AiAgent` получает одну или две реплики этой записи, контекст гостя и предыдущие ответы. Результат — одно намерение с параметрами. Например, для сдвига будильника модель возвращает направление и число минут, а новое время вычисляет concierge.
3. Concierge проверяет план по каталогу устройств. Для каждого изменения отправляет `POST /room/{session_id}/action` с временем `request.at` и сверяет время и значения в ответе симулятора. При сбое останавливает оставшиеся действия.
4. Гость получает один ответ. Класс `done` означает, что изменения подтверждены или требуемое состояние уже достигнуто. При невозможной, медицинской, посторонней или нераспознанной просьбе возвращается `refused`. При частичном выполнении ответ также получает `refused` и сообщает о частичном результате. В историю гостя записываются реплики и поля, изменение которых подтвердил симулятор. Следующая просьба может сослаться на конкретное значение, даже если ответ гостю был коротким. [Обработчик просьбы](../../src/concierge_service/service/request_handler.py)

## Ответ стенду

`Case2Answers` содержит два массива. В `stays` возвращаются идентификаторы записей и сеансов, в `requests` — те же идентификаторы и массив `replies`. Каждая реплика содержит роль, время, текст и класс ответа. Если создать сеанс не удалось, запись пропускается. Ошибка загрузки сценария также исключает этот заезд из ответа.

Из 45 минут пять секунд зарезервированы на формирование ответа. По истечении рабочего дедлайна после получения набора сервер возвращает HTTP 200 с завершёнными записями. Если набор ещё загружается, сервер возвращает HTTP 504. На dev ответ отдельно проверяет скрипт оценки через `/case/2/validate`. [HTTP-схемы](../../src/concierge_service/transport/http/schemas.py)
