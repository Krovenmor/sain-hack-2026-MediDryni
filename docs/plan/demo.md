# План Demo API

## Запуск

- По публичной ссылке открывается форма доступа с полями «Код показа» и «Код набора». Она отправляет `access_code` и `dataset_code` в теле `POST /api/v1/run_client`. Страница помечена как служебная и оформлена в цветах демо. Название проекта, превью и ресурсы экранов доступны после входа. Во время ожидания форма показывает индикатор и сменяющиеся фразы.
- Для нового Bearer бэкенд сверяет код показа с серверным `DEMO_ACCESS_CODE` до обращения к стенду и моделям. При пустой настройке вход закрыт. Пропущенный или неверный код даёт 403. Неудачные попытки ограничиваем по IP с ответом 429, чтобы замена Bearer не сбрасывала счётчик. Сам код не сохраняем в браузере и не пишем в логи.
- После проверки бэкенд запоминает допуск Bearer до конца показа и выдаёт браузеру cookie допуска (`HttpOnly`, `Secure`, `SameSite=Strict`). На одном HTTPS-домене сервер по этой cookie разрешает загрузку сборки демо, включая JS, CSS и изображения. Прямые ссылки на файлы тоже требуют допуска. Bearer по-прежнему определяет комнату для API.
- Для допущенного клиента бэкенд запрашивает `GET /case/2/getData?dataset_code=…` с серверным `HACK_TEAM_TOKEN`. Если набор недоступен, форма позволяет исправить его код. Выбор гостя показываем после `choose_stay`, интерфейс номера открываем после `ready`.
- Если в наборе один заезд, открываем его сразу. Если несколько, возвращаем `{status: "choose_stay", stays: [...]}`. Фронт показывает гостя по `user_id`, дату и время заселения. После выбора повторяет `run_client` с `dataset_code` и `stay_record_id`. До выбора комнату не занимаем.
- Набор загружаем один раз на `dataset_code`, предпочтения определяем для выбранного гостя, а сценарий считаем один раз на пару `(dataset_code, stay_record_id)`. Параллельные запросы одного сценария ждут общий расчёт.
- `GET /api/v1/demo/default-dataset` отдаёт публичную подсказку для поля кода набора, либо `null` до настройки. Команда задаёт или заменяет её через `PUT` на тот же адрес с командным Bearer и телом `{"dataset_code":"…"}`. Код хранится в памяти процесса до перезапуска. Поле остаётся доступным для редактирования. Допуск к демо по-прежнему требует кода показа.

### Комната для финала

Режим выбирает бэкенд по `dataset.meta.phase` из `getData`. Для `final` действуем по [инструкции организаторов](../case/for-teams-final.md).

1. После выбора заезда и подготовки общего плана для нового клиентского ключа вызываем `POST /runs {"case":2,"stage":"final"}`. Сразу закрепляем полученный `run_id` за ключом, сверяем `dataset_id` с загруженным набором. Для доступа к Room API используем серверный `HACK_TEAM_TOKEN` и при создании сеанса передаём `run_id`.
2. Вызываем `POST /room/session` с этим `run_id`, исходным `record_id` заезда и `kind="stay"`. Сохраняем `session_id` и публикуем исходный сценарий через `POST /room/{session_id}/scenario`. Время шагов и будильника берём из плана гостя. После подтверждения возвращаем `ready`.
3. Одновременные входы с одним ключом ждут одного запуска. Если прогон уже создан, а комната или публикация ещё не готовы, повтор продолжается с сохранённого шага. Перезагрузка готового клиента возвращает его комнату со всеми правками.

Пять судей могут выбрать один заезд. У каждого будет свой final-прогон и своя комната, а набор, предпочтения и исходное расписание будут общими. В final `reference` равен `null`, массив `requests` пуст. Просьбы поступают из чата во время показа. Прогон действует до 22 ноября, 23:59 МСК. Логические часы внутри комнаты идут от `check_in_at` до `target_wake_at`.

### Репетиция на dev

Для `phase=dev` используется проверенная схема 7.1. Один dev-прогон обслуживает несколько браузеров, каждому выделяется совместимый dev-заезд со сдвигом расписания. Ответ `409 demo_full` и срок 45 минут относятся к этому режиму.

По истечении dev-прогона API возвращает `410 dev_session_expired`. Браузер вызывает `POST /api/v1/demo/reset` со старым Bearer, сохраняет новый `client_key` и повторяет вход через `run_client` с сохранённым выбором. Повторный сброс того же ключа возвращает тот же ключ. Первый вход в новую комнату создаёт общий dev-прогон под блокировкой. Каждый браузер получает отдельную комнату с исходным планом, пустой историей и часами от заселения. Для final ответ `410 show_ended` завершает показ.

## Сессия клиента

Браузер один раз генерирует случайный ключ через `crypto.getRandomValues` (32 байта), сохраняет в `localStorage` и передаёт как Bearer в клиентских ручках. После успешного входа рядом сохраняются `dataset_code` и выбранный `stay_record_id`, чтобы при перезагрузке открыть ту же комнату. Вкладки одного браузерного профиля используют одну комнату. Ключи двух устройств дают разные комнаты.

Каталог общий для набора, предпочтения — для гостя, исходный план — для заезда. У ключа клиента свои `session_id`, часы, сообщения, расшифровки и ревизия. Сначала клиент ссылается на исходный план. При первой правке сохраняем его собственную версию расписания. Исходное аудио после распознавания освобождаем. По окончании показа очищаем клиентские данные.

## Управление

Часы принадлежат серверу. Старт и минимум — заселение, максимум — конец доступного интервала заезда. По умолчанию ход 1:1, на максимуме — пауза. Можно поставить на паузу или перемотать в обе стороны в этих границах. Перемотка сохраняет историю.

На главном экране часы показывают текущее демо-время. Ползунок перематывает при отпускании и возобновляет ход часов, если выбран момент до конца заезда.

Ручная правка меняет план выбранного периода. Будильник общий для заезда. Чат фиксирует время при получении сообщения: «сделай теплее» действует сейчас, «сделай ночью теплее» меняет ночной план. Вкладка на фронте на чат не влияет. Для живой просьбы переиспользуем `RequestHandler`: выделяем обработку в переданном сеансе с текущим снимком комнаты. Сегодня `handle()` сам открывает отдельный сеанс на каждую просьбу. [Обработчик](../../src/concierge_service/service/request_handler.py)

Ручной экран копит правки периода и будильника. При смене периода или уходе с экрана отправляет один PATCH с изменёнными полями. Переход выполняется сразу. Экраны показывают новые значения, пока PATCH выполняется в фоне. Запросы отправляются последовательно, при ошибке правки доступны для повторной отправки.

DemoService ведёт расписание каждого клиента в памяти процесса. Для команды «сейчас» отправляем `POST /room/{session_id}/action` и записываем подтверждённые поля в личный план на время команды. Следующий запланированный шаг для того же поля вступает в силу в своё время. Для правки будущего периода из чата или ручной настройки меняем нужные шаги личного плана и отправляем полное расписание через `POST /room/{session_id}/scenario`. После подтверждения обновляем ревизию и возвращаем её фронту. При частичном исполнении сохраняем только подтверждённые изменения. Карточки и `GET /stay/current` читают эту версию плана.

Просьбы с точным временем или задержкой добавляют разовый шаг в личное расписание.
Чат сразу подтверждает время после публикации сценария. Задержка отсчитывается от
логического времени при получении сообщения. Для времени без даты берём ближайшее
такое время в часовом поясе отеля. Если момент недоступен до конца заезда, просим
выбрать другое время. Перемотка показывает состояние комнаты на выбранный момент.

После трёх секунд тишины голосовая запись отправляется автоматически, если микрофон уже уловил речь. Второе нажатие на микрофон завершает запись сразу. Если речь не обнаружена, запись отбрасывается при завершении.

## Ручки клиента

В роутере `/api/v1` общая зависимость FastAPI читает клиентский Bearer и проверяет его формат (ошибка — 401). Только `run_client` принимает новый ключ. Остальные обработчики через `Depends(get_client_session)` получают готовую сессию по ключу или возвращают 401, если ключ неизвестен. Сервис берёт Room API `session_id` из этой сессии. Сообщения, записи и ответы для озвучки ищутся внутри неё, чужой ID даёт 404.

| Метод и путь | Контракт |
|---|---|
| `POST /demo/reset` | Bearer истёкшей dev-комнаты → `{client_key}`. Неизвестный ключ — 401, активная комната — 409, окончание final — 410. |
| `POST /run_client` | Первый вход передаёт `access_code` и `dataset_code`. Допущенный Bearer позволяет опустить `access_code` при выборе заезда и перезагрузке. Код набора обязателен (422), `stay_record_id` опционален. Ответ — список для выбора либо `{status: "ready", stay: …}`. Неизвестный заезд в наборе — 404. Повтор для открытой комнаты возвращает её по ключу, попытка сменить её набор или заезд — 409. |
| `GET /stay/current` | Гость, периоды с настройками, будильник, часы и ревизия плана. |
| `PATCH /stay/current` | Частичное изменение с одного экрана. Например, `{"revision":4,"periods":{"night":{"temperature":19,"curtains":0}},"alarm":{"time":"06:30"}}`. Периоды `evening`, `night`, `morning`, `day` принимают `temperature`, `curtains`, `doNotDisturb`, `kelvin` и `brightness`. Будильник принимает `time`, `enabled`, `soundOn`, `alarmLight`, `track` и `volume`. Проверяем весь набор полей, сохраняем план через Room API и возвращаем актуальный заезд. При устаревшей ревизии возвращаем 409. |
| `GET /room/state?at=…` | Возвращает `{at, state}` на указанное время или на серверное «сейчас». Просмотр оставляет часы на месте. |
| `GET /demo/clock`, `PATCH /demo/clock` | Чтение и изменение часов. PATCH принимает `at` и/или `paused`. В ответе обеих ручек есть `now, min, max, paused, period`. Главная выделяет карточку текущего `period` по серверным часам. Время вне границ — 422. |
| `GET /messages?limit=30&before=…` | По умолчанию последние 30 сообщений в порядке общения. Ответ `{items, next_before}`. Курсор ведёт к более старым сообщениям, в конце — `null`. |
| `POST /voice/recordings` | Принимает один файл в поле `file` формы `multipart/form-data` размером до 5 МБ. После распознавания через `gpt-transcribe` возвращает `{recording_id, text}` и сохраняет расшифровку в сессии клиента. |
| `POST /messages` | `client_message_id` и ровно одно из `text` или `recording_id`. Для голоса берём сохранённую расшифровку по ID. Возвращаем `{guest, reply, changes, revision}`. Реплики содержат `id`, `client_message_id`, `role`, `at` и `text`. Повтор с тем же ID и текстом возвращает прежний результат. Повтор с другим текстом даёт 409. |
| `GET /messages/{reply_id}/speech` | Синтез готового ответа через `tts-1`, в ответе MP3. Если озвучивание недоступно, текст и результат команды уже у клиента. [Инструкция по голосу](../case/voice-for-teams.md) |

## Порядок реализации

1. Проверить вход с одним заездом и выбор из нескольких. Для final открыть один заезд с пяти ключей, сверить пять разных пар `run_id` и `session_id` при одном расчёте сценария. Повторить вход с тем же ключом и проверить сохранность комнаты и расписания.
2. Чтение и единый PATCH заезда. Проверить, что после одной правки ручной экран, главная и сценарий показывают одинаковые значения.
3. Через чат понизить текущую температуру на градус и сверить ответ, карточку и снимок Room API. Затем задать температуру на ночь и проверить перемоткой значения до и после начала ночи. Повтор сообщения с тем же ID сохраняет ревизию и число действий.
4. Голос. Проверить полный путь с iPhone по HTTPS: запись → текст и ID → сообщение по ID → озвучка ответа.
