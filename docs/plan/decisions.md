# Решения по кейсу 2

## 1. Контекст просьб

**Решение: оставить последовательную обработку и пополнение истории.** Это правильная идея: реплика может ссылаться на предыдущую просьбу, а одинаковый pipeline нужен для `/run` и живого demo.

Для каждого пользователя хранится отдельный `ConversationContext`: исходный `chat_history` плюс уже обработанные в текущем запуске пары `utterances + replies`. Записи одного пользователя обрабатываются в исходном хронологическом порядке набора; после ответа текущая пара добавляется в контекст следующей записи.

Важно:
- 1–2 реплики одной записи приходят вместе, выражают один intent и передаются в одном AI-вызове;
- в историю попадают не сырые рассуждения LLM, а итоговые безопасные replies;
- история не смешивается между пользователями;
- conversation context переносится, а `RoomSession` и `initial_state` — нет: для каждой просьбы новый сеанс и собственный снимок устройств.

## 2. Batch или отдельные AI-вызовы

**Для просьб выбираем один вызов на `record_id`, а не общий batch всех 60 просьб.** Общий batch передаёт модели будущие реплики, усложняет восстановление порядка и делает pipeline отличным от production/demo. Один вызов на каждую из двух реплик не нужен — они обрабатываются вместе.

Оценка бюджета: 60 просьб — до 60 основных вызовов. При лимите 30 запросов/мин нужен rate limiter; чистое время отправки займёт около двух минут, что укладывается в 45 минут. Скрытые 400–500 reasoning tokens на вызов дают примерно 24–30 тыс. токенов на 60 вызовов плюс вход/выход, поэтому фактический расход нужно измерять на dev. `max_tokens` задаётся с запасом не менее 1000 сверх ожидаемого ответа. Retry невалидного JSON — максимум один, с учётом общего deadline. Инструкция предупреждает, что схема «один вопрос — один вызов» может исчерпать дневной лимит: при таком результате на dev допускаются bounded batch только для независимых просьб, а контекстные записи остаются последовательными.

Для preference hints приоритет — качество сценария. **В online MVP AI всегда анализирует ленту и историю диалога один раз на пользователя в рамках `/run`, независимо от заполненности профиля.** Core ждёт результат в рамках обычного timeout и общего deadline; специального soft deadline ради 10 секунд нет. Результат переиспользуется для заездов пользователя. Небольшие batch по пользователям допустимы: размер ограничивается token budget, ответ сверяется по `user_id`, ни один пользователь не исключается из анализа по признаку полноты профиля. Оптимизация с пропуском AI откладывается до готовности online и проверки её влияния на качество на dev. Десять секунд — вторичная метрика, а не причина отказаться от обогащения. Если просьбы окажутся слишком дорогими, следующая оптимизация — детерминированные обработчики очевидных intent и bounded batch независимых записей, а не объединение всего диалога в один запрос.

**Предпочтения разрешаются по приоритету «профиль → AI hints → дефолты».** Явно заданные структурированные значения приоритетнее противоречащих hints; hints дополняют недостающие сведения. Для параметров, оставшихся неизвестными, используются заранее заданные детерминированные дефолты, согласованные с R1–R8 и каталогом устройств и проверенные на dev. Это штатное поведение и при успешном ответе AI без полезных hints. При ошибке/timeout AI остаются профиль и те же дефолты.

## 3. Хранение контекста

**По умолчанию in-memory, один Uvicorn worker.** `/tmp` не нужен для штатного online `/run`, а запись пользовательских текстов на диск добавляет сериализацию и вопросы очистки. Контейнер эфемерный, поэтому персистентность между деплоями он всё равно не даст. Восстановление после перезапуска процесса в online MVP не реализуется.

Ограничение: перезапуск процесса очищает весь dialog/demo-контекст и обрывает незавершённый `/run`; повторного вызова на online не будет. Несколько Uvicorn workers без общего хранилища использовать нельзя.

## 4. Граница ответственности AI

Python-порт и DTO зафиксированы в `concierge_service/ports/ai.py`; подробные форматы и обработка ошибок — в [контракте AiAgent v1](../contracts/ai_agent.md). Проверку ответа модели и один retry невалидного ответа выполняет AI-адаптер. Core получает типизированный результат либо `AiAgentError` и выбирает fallback без дополнительного AI-вызова.

**AI отвечает за понимание просьбы, но не за её исполнение.** Он контекстно интерпретирует 1–2 utterances: определяет intent и slots, разрешает отсылки к предыдущему диалогу («передвинь его», «как вчера»), а также извлекает preference hints из ленты.

**Core отвечает за решение и фактический результат.** `ActionPlanner` превращает каждую интерпретацию в ноль или несколько действий: для `like_home` использует устойчивые предпочтения профиля, для `like_yesterday` — историю с общим `days_ago` (вчера по умолчанию, N дней назад без новых intent), для sleep/wake-намерений — настройки `SleepPlanner`. Затем core проверяет весь список по каталогу устройств и `initial_state`, вызывает симулятор и только затем выбирает `done|refused`. AI не возвращает готовые `/action` и не может объявить невыполненное действие успешным.

Core **не генерирует медицинские рассуждения и не «понимает медицину»**. `ReplyComposer` только выбирает заранее написанные шаблоны:
- для `medical` — фиксированный отказ без диагноза, лекарств, дозировок и обещаний эффекта;
- для `out_of_scope` и `invalid_value` — фиксированный отказ по коду причины;
- для `done` — шаблон с фактами подтверждённого действия, например «Установил температуру 20 °C».

Таким образом безопасность текста обеспечивается ограниченным набором шаблонов, а не медицинскими знаниями core. Советы ограничиваются правилами сна, а отель при упоминании называется только «партнёрский отель сна». На dev уникальные тексты дополнительно проходят `medcheck` с учётом его квоты. Если позже понадобятся более естественные формулировки, AI сможет перефразировать уже определённый core результат, но только с теми же ограничениями и обязательным template fallback; для MVP это лишний вызов и риск.
