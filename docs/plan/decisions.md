# Решения по кейсу 2

## 1. Контекст просьб

**Решение: оставить последовательную обработку и пополнение истории.** Это правильная идея: реплика может ссылаться на предыдущую просьбу, а одинаковый pipeline нужен для `/run` и живого demo.

Для каждого пользователя хранится отдельный `ConversationContext`: исходный `chat_history` плюс уже обработанные в текущем запуске пары `utterances + replies`. Записи одного пользователя обрабатываются в исходном хронологическом порядке набора; после ответа текущая пара добавляется в контекст следующей записи.

Важно:
- 1–2 реплики одной записи приходят вместе и передаются в одном AI-вызове;
- в историю попадают не сырые рассуждения LLM, а итоговые безопасные replies;
- история не смешивается между пользователями;
- conversation context переносится, а `RoomSession` и `initial_state` — нет: для каждой просьбы новый сеанс и собственный снимок устройств.

## 2. Batch или отдельные AI-вызовы

**Для просьб выбираем один вызов на `record_id`, а не общий batch всех 60 просьб.** Общий batch передаёт модели будущие реплики, усложняет восстановление порядка и делает pipeline отличным от production/demo. Один вызов на каждую из двух реплик не нужен — они обрабатываются вместе.

Оценка бюджета: 60 просьб — до 60 основных вызовов. При лимите 30 запросов/мин нужен rate limiter; чистое время отправки займёт около двух минут, что укладывается в 45 минут. Скрытые 400–500 reasoning tokens на вызов дают примерно 24–30 тыс. токенов на 60 вызовов плюс вход/выход, поэтому фактический расход нужно измерять на dev. Retry невалидного JSON — максимум один, с учётом общего deadline.

Для извлечения preference hints из ленты **небольшие batch по пользователям допустимы**: здесь нет последовательного диалогового перехода. Размер batch ограничивается token budget, ответ сверяется по `user_id`. Если просьбы окажутся слишком дорогими, следующая оптимизация — детерминированные обработчики очевидных intent, а не объединение всего диалога в один запрос.

## 3. Хранение контекста

**По умолчанию in-memory, один Uvicorn worker.** `/tmp` не даёт преимуществ для online `/run`, а запись пользовательских текстов на диск добавляет сериализацию и вопросы очистки. Контейнер всё равно эфемерный, поэтому внешняя персистентность не требуется. Файловый repository можно добавить позже за тем же портом только для локальной отладки.

Ограничение: перезапуск процесса очищает demo-контекст. Несколько Uvicorn workers без общего хранилища использовать нельзя.

## 4. Граница ответственности AI

**AI отвечает за понимание просьбы, но не за её исполнение.** Он контекстно интерпретирует 1–2 utterances: определяет intent и slots, разрешает отсылки к предыдущему диалогу («передвинь его», «как вчера»), а также извлекает preference hints из ленты.

**Core отвечает за решение и фактический результат.** Он проверяет slots по каталогу устройств, вычисляет patch от `initial_state`, вызывает симулятор и только затем выбирает `done|refused`. AI не должен иметь возможности объявить невыполненное действие успешным.

Core **не генерирует медицинские рассуждения и не «понимает медицину»**. `ReplyComposer` только выбирает заранее написанные шаблоны:
- для `medical` — фиксированный отказ без диагноза, лекарств, дозировок и обещаний эффекта;
- для `out_of_scope` и `invalid_value` — фиксированный отказ по коду причины;
- для `done` — шаблон с фактами подтверждённого действия, например «Установил температуру 20 °C».

Таким образом безопасность текста обеспечивается ограниченным набором шаблонов, а не медицинскими знаниями core. На dev тексты дополнительно проходят `medcheck`. Если позже понадобятся более естественные формулировки, AI сможет перефразировать уже определённый core результат, но только с теми же ограничениями и обязательным template fallback; для MVP это лишний вызов и риск.

Итоговая оценка исходного предложения: направление верное; уточнены изоляция контекста, момент обновления истории, цена 60 вызовов и отказ от `/tmp` как обязательного хранилища.
