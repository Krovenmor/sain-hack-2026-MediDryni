# Этап 7. Интерактивное демо

[План демо](../plan/demo.md) задаёт контракт ручек под `/api/v1`. Демо входит через `run_client`. Обработчик онлайн-прогона `/run` остаётся за рамками этапа.

В каждом шаге бэкенд и фронт можно делать параллельно. В начале шага согласуем пример ответа для UI. Пока ручка в работе, фронт использует этот пример. Для приёмки подключаем настоящий API, проверяем общий сценарий и отдаём шаг на ревью.

## 7.1. Вход и отдельная комната для каждого клиента

**Готово на dev.** Работают закрытый вход, выбор заезда, общий расчёт плана и возврат по ключу браузера. На стенде пять клиентов получили пять комнат в одном dev-прогоне для `stay_m7k2`.

**Ветка final реализована и проверена на тестовом наборе.** Организаторы выдадут код финального набора после сдачи решения. Для приёмки 7.1 перед сдачей используем результаты локальных интеграционных тестов. [Правила финала](../case/for-teams-final.md)

- **Бэкенд.** После проверки кода показа загрузить набор и выбрать режим по `dataset.meta.phase`. Для final создавать один прогон на клиентский ключ с `stage="final"`, выделять комнату по исходному ID выбранного заезда и публиковать общее расписание с исходными метками времени. Хранить прогресс запуска по ключу, чтобы повтор после сбоя публикации использовал уже полученные `run_id` и `session_id`.
- **Фронт.** Использовать существующую форму и ответы `choose_stay` / `ready`. При временном сбое дать повторить вход с тем же ключом. Если стенд завершил final-прогон, показать «Показ завершён».
- **Приёмка.** На тестовом final-наборе с `reference: null` и пустым `requests` пять ключей открывают один заезд. Ожидаем один расчёт, пять final-прогонов, пять разных комнат и исходное время будильника в каждой. Проверить одновременный вход из двух вкладок одного профиля, повтор после сбоя публикации и перезагрузку после `ready`.

## 7.2. Расписание, ручные настройки и часы

На ручном экране правки накапливаются до кнопки «Сохранить настройки». Одно сохранение отправляет значения из всех затронутых периодов и настройки общего будильника. Часы с паузой и перемоткой доступны на экране сценария.

- **Бэкенд.** Подключить `GET/PATCH /stay/current`, `GET/PATCH /demo/clock` и `GET /room/state?at=…`. При первой правке создать личную версию плана. Единым PATCH обновлять поля выбранных периодов и общий будильник, публиковать полное расписание через Room API. Учитывать подтверждение стенда и проверять ревизию при записи.
- **Фронт.** В `App.jsx` связать главную, сценарий, ручные настройки и выбор света с одним заездом из API. После сохранения применять ответ сервера, при конфликте ревизий перечитывать заезд. Подключить паузу и перемотку к серверным часам. Выбор вкладки периода служит только для просмотра и редактирования.
- **Приёмка.** Одним сохранением поменять температуру на ночь и время будильника. Проверить значения на экранах, после перезагрузки и в снимках комнаты до и после ночного шага. Устаревшая правка из второй вкладки получает 409. Пауза и перемотка в обе стороны действуют в пределах заезда, просмотр снимка оставляет часы на месте. У второго клиента сохраняются исходные значения и собственное время.

## 7.3. Текстовый чат и живые команды

- **Бэкенд.** Подключить `GET/POST /messages`, курсор истории и защиту от повторной отправки по `client_message_id`. Общий с `/run` интерпретатор за один вызов модели определяет действие и время применения. Чат фиксирует серверное время получения, берёт снимок целевого периода и при неоднозначности задаёт уточняющий вопрос. Для команды «сейчас» вызвать `action` и записать подтверждённые поля в личный план до следующего шага по этим полям. Будущую правку публиковать через `scenario`. Согласовать запись плана с ручным PATCH той же комнаты.
- **Фронт.** Отправлять текст и быстрые фразы через один обработчик. Показывать «Думает…» во время запроса, затем печатать полученный ответ через `useChatReply`. При повторе использовать прежний ID. После изменения расписания обновлять карточки. При открытии чата загружать последнюю страницу истории, более ранние сообщения получать по курсору.
- **Приёмка.** Выбрать вкладку «Утро», выставить на сервере вечер и попросить «сделай на градус прохладнее». Сверить ответ, карточку и текущее состояние комнаты. Попросить «ночью поставь 19 градусов», перемотать через начало ночи и проверить смену температуры. Повтор запроса оставляет по одной паре реплик и одному исполнению команды.

## 7.4. Голос поверх того же чата

В Chrome проверены запись с виртуального микрофона, воспроизведение MP3 и общая история. На dev-стенде синтезированная просьба прошла через Bifrost, изменила состояние номера один раз и получила озвученный ответ. Проверка на физическом iPhone остаётся частью репетиции.

- **Бэкенд.** Добавить `POST /voice/recordings` с лимитом 5 МБ. Вернуть текст и `recording_id`, освободить аудио после распознавания. В `POST /messages` принимать ровно одно из `text` и `recording_id`. По `GET /messages/{reply_id}/speech` отдавать MP3. Искать записи и ответы в сессии клиента. [Инструкция по голосу](../case/voice-for-teams.md)
- **Фронт.** Подключить запись из `useMicrophoneLevel`. Повторное нажатие микрофона завершает запись и отправляет файл. Показать расшифровку, отправить её ID в чат и заблокировать повторный ввод на время ответа. Вывести последнюю пару реплик в голосовом режиме, сохранить общую историю и воспроизвести озвучку.
- **Приёмка.** На iPhone по HTTPS произнести просьбу и проверить расшифровку, изменение комнаты, озвучку и одну пару реплик в обычном чате. При сбое синтеза остаётся текстовый ответ, команда выполняется один раз. Попытка получить чужую запись или озвучку возвращает 404.

## 7.5. Репетиция показа

На официальном dev-стенде один процесс бэкенда открыл пять комнат для одного заезда. Первый клиент изменил свет вручную, второй отправил голосовую команду через Bifrost, третий перемотал и остановил часы. После повторного входа сверили расписания, историю и снимки всех комнат. У остальных клиентов значения сохранились, повтор голосового запроса вернул прежний ответ.

| Замер на dev | Результат |
|---|---:|
| Первый вход с расчётом через модель | 31,17 с |
| Четыре последующих входа параллельно | 0,14 с |
| Сквозной прогон от запуска до проверки повторного входа | 36,36 с |
| Пиковая RSS бэкенда | 62,03 МиБ |

На мобильном размере в Chromium по HTTPS проверены запись, расшифровка, озвучка и история после обновления страницы. Использовался виртуальный микрофон. Тесты проверяют очистку записей и истории истёкшего клиента без нового запроса, а также доступность длинного dev-заезда после открытия короткого.

Физический iPhone и полный 15-минутный прогон с телефона остаются проверками на устройстве. Для проверки изоляции финального режима перед сдачей используем тестовый final-набор, поскольку код реального набора выдадут после сдачи.
