# План Demo API

## Запуск

- **Стенд** вызывает `POST /run` с `run_token`. Бэкенд передаёт этот токен в `getData`: успешный ответ подтверждает доступ к набору. Дальше работает обычный `RunCase`. Для финального показа сохраняем в памяти гостя, предпочтения и готовые шаги заезда, чтобы клиент открыл именно этого гостя.
- **Команда** может запустить демо тем же `POST /run` с `HACK_TEAM_TOKEN` с бэкенда. Для локальной репетиции берём заезд из dev-набора, определяем предпочтения и один раз вызываем `SleepPlanner.plan`. Готовые просьбы из набора пропускаем. На финале используем уже подготовленный сценарий.
- **Интерактивная комната** открывается при первом обращении клиента к текущему заезду перед показом. С командным токеном бэкенд вызывает `POST /runs {"case":2}`, затем `POST /room/session` с `run_id`, совместимым dev-`record_id` и `kind="stay"`. Загружаем план, переводя даты финального гостя в интервал dev-сеанса. Один показ использует один dev-прогон. Через 45 реальных минут сеанс истекает. Для следующего показа команда запускает демо заново. [Контракт стенда](../contracts/openapi.json)

## Управление

Часы принадлежат серверу. Старт и минимум — заселение, максимум — конец доступного интервала заезда. По умолчанию ход 1:1, на максимуме — пауза. Можно поставить на паузу или перемотать в обе стороны в этих границах. Перемотка сохраняет историю.

Ручная правка меняет план выбранного периода. Будильник общий для заезда. Чат фиксирует время при получении сообщения: «сделай теплее» действует сейчас, «сделай ночью теплее» меняет ночной план. Вкладка на фронте на чат не влияет. Для живой просьбы переиспользуем `RequestHandler`: выделяем обработку в переданном сеансе с текущим снимком комнаты. Сегодня `handle()` сам открывает отдельный сеанс на каждую просьбу. [Обработчик](../../src/concierge_service/service/request_handler.py)

## Ручки клиента

Общий префикс — `/api/v1`. Один активный заезд хранится в памяти бэкенда.

| Метод и путь | Контракт |
|---|---|
| `GET /stay/current` | Гость, периоды с настройками, будильник, часы и ревизия плана. |
| `PATCH /stay/current` | Частичное изменение с одного экрана. Например, `{"revision":4,"periods":{"night":{"temperature":19,"curtains":0}},"alarm":{"time":"06:30"}}`. Проверяем весь набор полей, сохраняем план через Room API и возвращаем актуальный заезд. При устаревшей ревизии — 409. |
| `GET /room/state?at=…` | Состояние устройств на указанное время или на серверное «сейчас». Просмотр оставляет часы на месте. |
| `GET /demo/clock`, `PATCH /demo/clock` | Чтение и изменение часов. PATCH принимает `at` и/или `paused`, возвращает `now, min, max, paused`. Время вне границ — 422. |
| `GET /messages?limit=30&before=…` | По умолчанию последние 30 сообщений в порядке общения. Ответ `{items, next_before}`. Курсор ведёт к более старым сообщениям, в конце — `null`. |
| `POST /voice/recordings` | Аудиофайл до 5 МБ → `gpt-transcribe` → `{recording_id, text}`. Бэкенд сохраняет расшифровку для текущего заезда, фронт сразу показывает текст. |
| `POST /messages` | `client_message_id` и ровно одно из `text` или `recording_id`. Для голоса берём сохранённую расшифровку по ID. Возвращаем реплики гостя и ассистента и подтверждённые изменения. Повтор с тем же ID сообщения возвращает прежний результат. |
| `GET /messages/{reply_id}/speech` | Синтез готового ответа через `tts-1`, в ответе MP3. Если озвучивание недоступно, текст и результат команды уже у клиента. [Инструкция по голосу](../case/voice-for-teams.md) |

## Порядок реализации

1. Запуск, перенос плана и часы. На dev проверить запись действия и чтение состояния до и после перемотки.
2. Чтение и единый PATCH заезда. Проверить, что после одной правки ручной экран, главная и сценарий показывают одинаковые значения.
3. Чат в существующем сеансе, история, повтор запроса без двойного действия.
4. Голос. Проверить полный путь с iPhone по HTTPS: запись → текст и ID → сообщение по ID → озвучка ответа.
