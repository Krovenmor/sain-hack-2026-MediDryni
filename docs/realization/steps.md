# Этапы реализации

Этапы 1-6 готовят бэкенд к онлайн-проверке, этап 7 добавляет API для финального показа. Каждый этап заканчивается проверкой результата и ревью. [Общий план](../plan/plan.md)

## Этап 1. Каркас и загрузка набора

Собрать приложение в `di/container.py`, вынести настройки в `di/config.py`, подключить FastAPI и `start.sh`. Реализовать `/health`, авторизацию `/run`, адаптер Hack API и преобразование входных данных в доменные записи. В `domain/dataset.py` построить индексы и проверить ссылки между записями.

**Приемка.** Сервер запускается, `/health` отвечает 200. На моке Hack API проверяются токен, код кейса, вызов `getData` и форма промежуточного ответа `{"stays": [], "requests": []}`.

## Этап 2. Сценарии заездов

Подключить Room API для создания сеансов, загрузки сценария, чтения состояния и журнала. Реализовать `SleepPlanner` с правилами R1-R8 и проверкой времен и значений по каталогу устройств. Первые сценарии строятся по профилю и значениям по умолчанию.

**Приемка.** Проверить смену даты и часового пояса, сокращенный вечерний период при позднем заселении, рассвет и явное выключение звука по таймеру. Симулятор принимает сценарии заездов на dev, по журналам можно проверить S.

## Этап 3. Извлечение предпочтений

Подключить порт `AiAgent` к concierge через мок и реализовать объединение профиля и подсказок. Затем подключить извлечение из ленты и диалога через LLM, проверку источников и отдельные результаты для каждого гостя. [Контракт AiAgent](../contracts/ai_agent.md)

**Приемка.** Проверить приоритет явного профиля, пустые подсказки, изоляцию гостей, ошибку одного профиля, таймаут всей операции и повторное использование предпочтений для нескольких заездов. Сверить сценарии на dev.

## Этап 4. Обработка просьб с моком AI

Добавить историю диалога в памяти, сеанс для каждой просьбы и планирование простых действий со светом, климатом, звуком и шторами. Подключить проверку плана по каталогу, исполнение через Room API и шаблоны итоговых ответов.

**Приемка.** На dev получается полный ответ, который принимает `validate`. Тесты покрывают сохранение незатронутых полей, сеанс для отказа, частичное выполнение составной просьбы и сбой отдельного сеанса.

## Этап 5. Интерпретация просьб через LLM

Подключить `interpret_request` и довести обработку до всех 19 намерений. Покрыть будильник, выбор звука, домашние настройки, просьбы о прошлых заездах, режимы сна и пробуждения. Для `like_yesterday` выбирать подтвержденные настройки за нужный календарный день в поясе отеля. Для медицинских и посторонних просьб подготовить шаблоны отказа.

**Приемка.** Проверить намерения и их параметры, уточнения к предыдущим просьбам, отсутствие истории и недопустимые значения. Сопоставить журналы dev с эталоном для C и S. Проверить уникальные тексты через `medcheck`.

## Этап 6. Надежность и готовность к онлайн-проверке

Ограничить параллелизм диалогов и частоту обращений к модели. Учесть повторы в бюджете, ввести общий дедлайн и диагностику ошибок по записям. Проверить запуск из архива деплоя.

**Приемка.** Выполнить полный dev-прогон через `start.sh`, получить `valid: true`, измерить C, S, расход токенов, пиковую память и длительность. Деплой выполняет команда. [Результаты и диагностика](stage6-review.md)

## Этап 7. Demo API после онлайн-проверки

Клиент открывает демо через `POST /api/v1/run_client`. Concierge один раз готовит исходный сценарий и выделяет каждому клиенту свою комнату в dev-прогоне. Контракты и порядок реализации описаны в [плане демо](demo.md).
