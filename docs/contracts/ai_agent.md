# Контракт AiAgent v1

Контракт для независимой реализации `ai_service`. Python-порт и DTO находятся в
[`services/concierge_service/ports/ai.py`](../../services/concierge_service/ports/ai.py).
Импорт при `services/` в `PYTHONPATH`: `from concierge_service.ports.ai import AiAgent`.
`AiAgent` — `Protocol`, а не готовый LLM-клиент. Реализация располагается в
`services/ai_service/service/agent.py`; наследоваться от протокола необязательно.
Composition root создаёт реализацию и передаёт её потребителям как `AiAgent`.

Внешний [`openapi.json`](openapi.json) определяет входные данные, каталог устройств
и 19 intent. Он **не определяет** внутренние AI hints, slots, ошибки и retry.
Эти решения зафиксированы здесь и в Python DTO. Это внутрипроцессный async-вызов;
дополнительный HTTP API между модулями не нужен.

## Граница ответственности

- Core получает и валидирует dataset, выделяет данные пользователя, хранит диалог,
  разрешает предпочтения, задаёт дефолты, рассчитывает R1–R8 и действия устройств.
- AI извлекает подтверждённые предпочтения и интерпретирует одну просьбу целиком.
  Он не вызывает Hack API, не возвращает команды `/action`, сценарий, replies или
  `response_class`, не применяет дефолты и не объявляет просьбу выполненной.
- AI-адаптер использует только `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`.
  Эти настройки передаются при сборке реализации; токены Hack API и `reference`
  не входят в аргументы методов и не попадают в промпты.
- Общие DTO принадлежат потребителю — `concierge_service/ports/ai.py`.
  Внутренние классы `ai_service` не пересекают эту границу.

## Входные данные

`ProfileContext` и `RequestContext` — dataclass-контейнеры. Внешние записи внутри
них передаются как JSON-объекты с оригинальными именами полей, строками дат и `null`.
Их структура определяется OpenAPI, а не повторной копией схемы в AI-порте.
Core проверяет их до вызова. Сам конструктор dataclass эту проверку не выполняет.
AI не изменяет переданные объекты.

| Поле `ProfileContext` | Источник в `Case2Dataset` |
| --- | --- |
| `user` | Одна запись `users[]`, включая `sleep_preferences` и текстовый `dislikes` |
| `events` | Только `events[]` этого пользователя, по времени; сохраняются `event_id`, `type`, `source`, `payload` |
| `chat_history` | Только исходные `chat_history[]` этого пользователя, по времени; сохраняются `message_id` |
| `devices` | Весь `devices[]`, включая `value_schema`, `default_value`, `unit` |
| `tracks` | Весь `tracks[]` |

В `RequestContext` дополнительно передаются:

| Поле | Значение |
| --- | --- |
| `profile` | Описанный выше `ProfileContext` |
| `request` | Одна исходная запись `requests[]`, включая `record_id`, `at`, `initial_state`, все 1–2 `utterances` |
| `stay` | Запись `stays[]`, соответствующая `request.stay_id`; содержит часовой пояс отеля и целевой подъём |
| `intents` | Все описания из `dataset.intents[]`; семантика сверяется с ними |
| `conversation` | Только уже обработанные в этом `/run` просьбы и ответы пользователя: `DialogueMessage(role, at, text)` в порядке диалога |
| `preference_hints` | Результат извлечения для пользователя либо `None`, если извлечение не удалось |

Исходная история уже есть в `profile.chat_history`: в `conversation` она повторно
не включается. Текущие utterances находятся только в `request`; будущие просьбы не
передаются. `initial_state` текущей просьбы имеет приоритет над состояниями, которые
можно предположить по предыдущим ответам. Переход к другой просьбе не переносит
состояние комнаты. Все записи контекста относятся к одному пользователю.

## Извлечение предпочтений

```python
async def extract_preference_hints(
    self, items: Sequence[ProfileContext], *, timeout_s: float
) -> Sequence[PreferenceResult]: ...
```

В MVP анализ проводится для каждого пользователя независимо от полноты профиля.
Core передаёт каждого пользователя один раз на извлечение в рамках `/run`;
внутренние retry не считаются новым извлечением. Можно передать несколько
пользователей: адаптер сам выбирает размер LLM batch в пределах бюджета.

Результат — ровно одна запись на входного пользователя **в том же порядке**, с тем
же `user_id`, без пропусков и дублей. Пустой вход даёт пустой результат без LLM.
Успех — `PreferenceHints`, индивидуальный сбой — `PreferenceFailure(user_id, error)`.
При сбое всего вызова допустим `AiAgentError`; core применяет fallback ко всем
пользователям без результата.

Все поля `PreferenceHints` обязательны; неизвестные значения передаются как `null`,
а `settings` — как `[]`, если наблюдений нет. Каждое известное значение обёрнуто в
`Hint(value, sources)`. Источник — `SourceRef(kind, source_id, pointer)`:

- `profile`: `source_id` равен `user.user_id`, `pointer` указывает поле профиля,
  например `/sleep_preferences/dislikes/0`;
- `event`: `source_id` равен переданному `event_id`;
- `message`: `source_id` равен переданному `message_id`;
- `pointer` — JSON Pointer внутри выбранной записи; пустая строка обозначает всю
  запись. Источник должен действительно подтверждать значение.

| Поле hints | Значение |
| --- | --- |
| `temperature` | `cool`, `normal` или `warm` |
| `light_sensitive` | Явная чувствительность к свету |
| `favorite_track_ids` | Известные ID из `tracks`; без дублей |
| `gentle_alarm` | Нужен ли мягкий будильник; «не люблю резкий звук» → `true` |
| `weekday_bedtime`, `weekday_wake_time` | Привычное домашнее время `HH:MM`, без поправки R8 |
| `home_timezone` | Домашняя IANA-зона, только если известна из входа |
| `settings` | Подтверждённые настройки для `like_home`, `like_yesterday`, `going_to_bed` и `woke_up` |

`null` отличается от подтверждённых `false` и `[]`: отсутствие упоминания звуков
не означает «любимых звуков нет». При конфликте извлечённых сведений, который
нельзя разрешить по явной коррекции пользователя или времени, значение остаётся
неизвестным. Приоритет структурированного профиля и дефолты применяет core.

`ObservedSetting` содержит `context=home|past_stay|bedtime|wake_up`, `observed_at`, `device_id`,
`field_id`, `value`, `sources`. Это факт из истории, не готовый patch устройства.
Для прошлой настройки используется время, к которому относится описанный факт,
а не автоматически дата заметки; если его нельзя установить, `observed_at=null`.
Разные прошлые настройки сохраняются отдельными наблюдениями.

Контексты `bedtime` и `wake_up` содержат конкретные настройки подтверждённого режима
сна и подъёма. Источник может подтверждать и привычку, и применение настройки
в конкретный заезд. В этом случае сохраняются два наблюдения в соответствующих контекстах.
Явная смена привычки обновляет настройку режима. История применения сохраняется.
При `woke_up` core снимает будильник, сохраняя его режим и окно срабатывания.
AI не подставляет сегодняшнюю дату вместо неизвестного «вчера». Core выбирает наблюдения
относительно времени просьбы и `like_yesterday.slots.days_ago`; отсутствие данных не
выдаётся за восстановленный факт.

## Интерпретация просьбы

```python
async def interpret_request(
    self, item: RequestContext, *, timeout_s: float
) -> RequestInterpretation: ...
```

Результат — объект `{record_id, intent, slots}`. `record_id` точно совпадает с
входным. Один intent относится сразу ко всем 1–2 репликам записи. Вторая реплика
может уточнять первую. Core формирует один итоговый ответ на запись после исполнения.
Отсылки к прошлому диалогу разрешаются по переданному контексту.

| Intent | Slots и единицы |
| --- | --- |
| `brighter`, `dimmer` | `mode=relative, amount` — положительное изменение яркости в процентных пунктах, направление задаёт intent; либо `mode=absolute, value` — заданная яркость |
| `warmer`, `cooler` | Та же форма, значения в °C, относятся только к климату |
| `quieter` | Та же форма, громкость в процентных пунктах |
| `sound_on` | `track_id`, `volume`, `timer_minutes`; каждое неуказанное значение — `null`. Для трека core последовательно проверяет любимые треки, подтверждённый трек для засыпания и текущий или стандартный трек. |
| `curtains` | `position`: 0 — закрыты, 100 — открыты, либо явно названная позиция |
| `alarm_set` | `target_at`: абсолютная дата и время с offset; опционально `alarm_mode=light|sound|both` и `window_minutes` |
| `alarm_shift` | `mode=relative, minutes`: положительное — позже, отрицательное — раньше; либо `mode=absolute, target_at`; опционально `alarm_mode` и `window_minutes` |
| `do_not_disturb` | `enabled`: boolean |
| `all_off`, `alarm_cancel`, `going_to_bed`, `woke_up`, `like_home` | Пустой объект `{}`; настройки режима рассчитывает core |
| `like_yesterday` | `days_ago`: необязательное целое `>= 0`; отсутствие/`null` означает вчера, `N` — N календарных дней назад в часовом поясе отеля. Это общий параметр существующего intent, а не новые intent'ы `like_n_days_ago`/`like_n_trips_ago`; прошлый заезд сводится к известному числу дней, иначе — `unresolved_reference` |
| `medical`, `out_of_scope` | Пустой объект `{}`; шаблон отказа выбирает core |
| `invalid_value` | `subject`, исходное `requested_value`, `reason=out_of_range|unknown_track|unsupported_mode|invalid_time` |

«Сделай теплее» → `warmer` с `{"mode":"relative","amount":null}`. Числовой
шаг выбирает core. «На два градуса прохладнее» → `cooler` с `amount=2`.
В относительных значениях яркости/громкости процент означает процентный пункт;
неоднозначное «вдвое» нужно разрешить относительно `initial_state` в абсолютное
значение. AI не заменяет отсутствующее число произвольным шагом.

`alarm_mode` и `window_minutes` заполняются только при указании пользователя,
иначе `null` или отсутствие поля. Это семантические названия внутри порта;
core сопоставляет режим со значениями каталога и сохраняет незатронутые поля.

Для абсолютного времени будильника AI учитывает `request.at`, часовой пояс отеля,
дату и контекст диалога. Неуказанная дата — ближайшее будущее вхождение указанного
местного времени; явно названная дата сохраняется. Core повторно проверяет
полученное время. При неразрешимой отсылке/неоднозначности —
`AiAgentError("unresolved_reference")`, а не выдуманное значение и не ложный `out_of_scope`.

Недопустимое явное значение, например 35 °C, не обрезается до границы каталога:
AI возвращает `invalid_value` с исходным значением. Числовые DTO намеренно не
зашивают диапазоны устройств: они определяются `devices[].fields[].value_schema`.
Core независимо проверяет весь план перед выполнением, даже после успешного AI.
`subject` и `requested_value` описывают неверный пользовательский ввод; core не
вставляет их в пользовательский текст без проверки и не считает ID устройства.

Для JSON-ответа модели используются `REQUEST_INTERPRETATION_ADAPTER.validate_json`
и `PreferenceHints.model_validate_json`. JSON Schema доступна через
`REQUEST_INTERPRETATION_ADAPTER.json_schema()` и `PreferenceHints.model_json_schema()`.
Это схема полезной нагрузки, без оболочки ответа `/chat/completions`.

```json
{
  "record_id": "request_1",
  "intent": "alarm_shift",
  "slots": {"mode": "relative", "minutes": 30}
}
```

## Проверки, ошибки и время

Pydantic запрещает лишние поля, неизвестные intent, несовместимые slots,
строки вместо чисел, нечисловые `NaN`/Infinity и даты без явного offset (включая `Z`).
Адаптер **дополнительно** проверяет совпадение ID результата со входом, принадлежность
источников пользователю, существование JSON Pointer, ID треков/устройств/полей,
отсутствие дублей треков и корректность IANA-зоны. Эти контекстные проверки не
заменяются JSON Schema. Ошибочный ответ модели не возвращается потребителю как успех.

- `timeout_s > 0` — общий бюджет вызова, включая ожидание семафора, rate limiter,
  сеть и retry. При извлечении предпочтений core оставляет небольшой запас до
  внешнего дедлайна, чтобы адаптер успел вернуть готовые результаты и отметить
  пользователей, для которых бюджет истёк.
- Один повтор после невалидного JSON/DTO/контекстных ссылок выполняет **AI-адаптер**.
  Core повторно AI не вызывает: использует детерминированный fallback или отказ.
- Одиночное извлечение предпочтений начинается с `max_tokens=10000`. При
  `finish_reason=length` разрешённый повтор использует `16000` и исходный промпт.
  Лимит пачки равен `10000 × число профилей`: `20000` для двух и `30000` для трёх.
  Ошибка JSON, схемы или ссылок повторяется с исходным лимитом и инструкцией
  на исправление. Повтор пакета по отдельным профилям расходует их попытку повтора.
- 429 обрабатывается адаптером с `Retry-After`/backoff только в пределах бюджета.
  Все попытки учитываются общим rate limiter реализации; лимит не отдельный на метод.
- Ожидаемые ошибки: `timeout`, `rate_limited`, `unavailable`, `invalid_response`,
  `unresolved_reference`. При завершении повторов — `AiAgentError(code)` либо
  `PreferenceFailure` для отдельного пользователя batch. Медицинская просьба и
  недопустимое значение — штатные результаты интерпретации, а не ошибки AI.
- Реализация поддерживает конкурентные вызовы разных пользователей и не хранит
  общую историю разговора. Отмена coroutine распространяется наружу; фоновые
  запросы после timeout не продолжаются. Секреты, входные данные, промпты и ответы
  модели не включаются в логи или сообщения исключений.

## Локальная проверка ai_service

Системные промпты хранятся в [`services/ai_service/prompts/`](../../services/ai_service/prompts/).
Команды запускаются из корня проекта с `LLM_BASE_URL`, `LLM_API_KEY` и `LLM_MODEL` в окружении.

```sh
PYTHONPATH=services python -m ai_service.cmd.check_proxy
PYTHONPATH=services python -m ai_service.cmd.evaluate_dev --dataset-file docs/data/dataset.json
```

`check_proxy` делает один пробный запрос к прокси. `evaluate_dev` по умолчанию
берёт до восьми просьб попеременно у двух пользователей и сохраняет
хронологию каждого диалога. В отчёте есть число совпадений intent и статистика
вызовов. Для проверки слотов, действий в симуляторе и оценок C/S нужен сквозной dev-прогон.
Эталон используется только для сверки результата.

Минимальная приёмка: все 19 intent; `like_yesterday` с вчера, N дней назад и
неразрешимой датой; две реплики и отсылка к предыдущей просьбе;
невалидное значение без обрезания; пустые hints как успех; источники только своего
пользователя; индивидуальная ошибка batch; один retry невалидного ответа; timeout,
429 и отмена; отсутствие вызовов симулятора. Семантика составных режимов и
конкретные дефолты остаются ответственностью core и сверяются на dev.

Проверка DTO без сети из корня репозитория:

```sh
PYTHONPATH=services python -m unittest discover -s tests -p 'test_ai_contract.py' -v
```

Эти тесты проверяют формы ответов и соответствие списка intent внешнему контракту.
Качество NLU, источники относительно реального входа и поведение сетевого адаптера
проверяются отдельно при его реализации.
